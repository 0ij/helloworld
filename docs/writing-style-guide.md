# 技术文章写作规范

这份文档用于约束本站技术文章的写法，目标是让内容更接近成熟技术文档和专业专栏，而不是口语化随笔或“AI 总结稿”。

适用范围：

- `src/content/blog/` 下的新文章
- 对既有文章的改写和补充

## 1. 写作目标

文章应优先满足以下目标：

1. 把概念定义清楚。
2. 把问题边界说清楚。
3. 把推荐做法和不推荐做法区分清楚。
4. 在必要处给出最小可执行示例。
5. 让读者能据此落地，而不是只获得抽象印象。

## 2. 推荐的文章结构

优先使用下面这种结构组织内容：

1. 背景
2. 概念或机制定义
3. 常见实现方式
4. 适用场景与约束
5. 推荐方案
6. 落地建议或示例

不是每篇文章都必须完整覆盖六部分，但至少要保证“定义”和“落地”同时存在，避免只讲概念或只给代码片段。

## 3. 语言风格

### 3.1 应该采用的风格

- 使用陈述句，少用感叹、反问和口语化推进。
- 优先解释事实、机制和约束，再给判断。
- 段落尽量短，但信息密度要高。
- 术语尽量稳定，同一篇文章里避免来回换说法。
- 对比时写清楚比较维度，例如性能、维护性、兼容性、可访问性。

### 3.2 应避免的表达

以下表达会明显增加“AI 味”或“博客随笔感”，应尽量避免：

- “先说结论”
- “我觉得 / 我个人理解是”
- “最后收一下”
- “如果只给一个答案”
- “其实没有那么复杂”
- “本质上就是”
- 连续使用设问句推进全文
- 大段价值判断，但不给依据

这类表达不是完全禁止，但不应成为文章主干。

## 4. 内容组织规则

### 4.1 先定义，再展开

第一次出现的重要概念，优先先写清楚定义，再写实现方式。

例如：

- 写字体时，先定义 `font-family` 的匹配逻辑，再讲 `@font-face`
- 写图标时，先区分 iconfont 和 SVG，再讲封装
- 写架构时，先定义边界、依赖方向和变化点，再谈实践

### 4.2 结论必须绑定条件

不要写无条件的大结论，要补上适用前提。

不推荐：

```text
新项目一定要用 SVG。
```

推荐：

```text
如果没有明确的历史包袱，新项目通常更适合优先采用 SVG。
```

### 4.3 对比必须落到维度

不要只写“更好”“更灵活”“更现代”，要说明是在哪个维度更好。

不推荐：

```text
SVG 比 iconfont 更好。
```

推荐：

```text
SVG 在多色表达、组件化集成、可访问性和调试体验上通常优于 iconfont。
```

### 4.4 列表要有分类依据

列点时应让每一项属于同一分类维度，避免把“原因、现象、建议、结论”混在同一组列表里。

## 5. 示例规范

### 5.1 示例要最小化

示例代码只保留当前论点必需的部分，不为了“完整”引入无关细节。

### 5.2 示例要服务于解释

代码片段前后要说明：

- 这个示例在说明什么
- 为什么这样写
- 需要注意什么限制

### 5.3 示例风格要接近真实项目

避免为了看起来高级而写过度抽象的示例。示例应优先接近真实业务中会出现的写法。

## 6. 工程类文章的重点

如果文章涉及工程实践，至少应覆盖下面三类信息中的两类：

- 机制：浏览器、框架、工具是怎么工作的
- 约束：为什么某种写法会出问题，限制在哪里
- 方案：项目里应该怎么组织代码、目录、配置或组件

只给“经验判断”而不解释机制，容易变成口号。
只讲机制而不给方案，落地价值会很弱。

## 7. 引用和参考

涉及规范、浏览器行为、框架 API 或工具能力时，优先参考官方资料，例如：

- MDN
- web.dev
- 框架官方文档
- 官方 RFC / 设计说明

引用资料的作用是校准术语和机制解释，不是把文章写成资料摘录。

## 8. 文章结尾写法

结尾不需要“金句式总结”，也不需要强行升华。

优先使用下面两种结束方式之一：

1. 回到工程落地，明确项目中要先定哪些规则。
2. 回到主题边界，说明本文覆盖了什么、没有覆盖什么。

不推荐的结尾方式：

- 情绪化收束
- 大而空的价值判断
- 重复前文已经说过的六七条结论

## 9. 发布前自检清单

写完一篇文章后，至少检查以下问题：

1. 文章开头是否在前两三段内说明了主题范围。
2. 重要术语是否先定义后使用。
3. 是否存在连续多段“我觉得”“可以理解为”“其实就是”。
4. 结论是否都带有适用条件。
5. 列表是否属于同一分类维度。
6. 示例是否足够小，且解释了用途。
7. 结尾是否仍然像聊天，而不是文档。

## 10. 一个简化判断标准

如果一段话更像下面左边，通常要继续修改：

- 像聊天
- 像演讲稿
- 像总结稿
- 像泛化经验

如果一段话更像下面右边，通常方向是对的：

- 像文档
- 像设计说明
- 像技术评估
- 像项目约定
