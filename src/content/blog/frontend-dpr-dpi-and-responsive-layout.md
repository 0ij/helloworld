## 1. 这组概念为什么总是被讲乱

前端里关于像素的讨论，常见的问题不是术语太多，而是把不同层面的概念混在了一起。

比如下面这些说法，经常被放在一段话里：

- 这台设备是 `3x` 屏
- 这个页面宽度是 `390px`
- 这张图要出 `2x`、`3x`
- 这个设计稿是 `1170px`
- 这个设备 `DPI` 很高

这些话单独看都没错，但它们分别描述的是不同层面：

- 硬件屏幕有多少物理像素
- 浏览器用什么逻辑单位做布局
- 当前设备的像素密度有多高
- 图片资源应该提供多大尺寸

如果这几层没有分开，后面讨论响应式布局时就很容易走偏。很多人会自然得出一个错误直觉：

> 页面在高分屏上变清晰，是因为浏览器直接拿物理像素做布局。

实际不是这样。浏览器做布局时依赖的是 CSS 像素，物理像素主要在绘制阶段起作用。

这篇文章只做一件事：把这条链路讲清楚，然后说明为什么响应式布局应该围绕逻辑宽度展开，而不是围绕设备型号展开。

## 2. 先把几个名词拆开

### 2.1 物理像素

物理像素是屏幕硬件上的真实像素点。

设备参数里的分辨率，例如：

```text
1170 x 2532
1920 x 1080
2560 x 1600
```

说的都是物理像素数量。

这是硬件层概念。前端代码不能直接控制它。

### 2.2 CSS 像素

CSS 像素是浏览器做布局时使用的逻辑单位。

页面里写的：

```css
.card {
  width: 320px;
  padding: 24px;
  font-size: 16px;
}
```

这里的 `px` 默认都是 CSS 像素。

CSS 像素不是硬件像素，也不是“屏幕上真的 1 个点”。它的作用是给浏览器提供一个相对稳定的布局单位，让页面开发不必直接面向具体屏幕硬件。

### 2.3 PPI 和 DPI

这两个概念经常被混用，但原始含义并不完全一样。

- `PPI`：Pixels Per Inch，每英寸像素数，更适合描述屏幕像素密度
- `DPI`：Dots Per Inch，每英寸点数，原本更常用于打印设备

前端讨论屏幕清晰度时，更准确的词通常是 `PPI`。但在 Web 工程里，真正直接影响渲染策略的往往不是 `PPI` 本身，而是 `DPR`。

### 2.4 DPR

`DPR` 是 `devicePixelRatio`，表示设备像素比：

```text
DPR = 物理像素 / CSS 像素
```

它描述的是：

> 一个 CSS 像素在当前设备上，会映射到多少个物理像素。

例如：

- `DPR = 1`：1 个 CSS 像素大致映射到 1 个物理像素
- `DPR = 2`：1 个 CSS 像素大致映射到 2 x 2 个物理像素
- `DPR = 3`：1 个 CSS 像素大致映射到 3 x 3 个物理像素

浏览器里可以直接读这个值：

```js
window.devicePixelRatio
```

这里有一个容易被忽略的细节：`devicePixelRatio` 不一定总是整数。浏览器缩放、系统缩放和某些显示环境下，它可能是 `1.25`、`1.5`、`2.625` 这样的值。

## 3. 浏览器到底是怎么把 CSS 像素画到屏幕上的

这一段是核心。

页面渲染大致可以拆成两步：

1. 布局阶段：浏览器使用 CSS 像素计算盒模型、字体、间距和排版
2. 绘制阶段：浏览器把这些逻辑结果映射到物理像素上显示

关键点在于：

> 布局发生在 CSS 像素层，清晰度差异主要体现在 CSS 像素如何映射到物理像素层。

### 3.1 先看一个具体例子

假设一台手机：

- 物理分辨率宽度约为 `1170`
- `DPR = 3`

那么它的逻辑宽度大致就是：

```text
1170 / 3 = 390 CSS px
```

如果页面里有这样一个盒子：

```css
.box {
  width: 100px;
  height: 40px;
}
```

浏览器首先会把它当成：

- 宽 `100 CSS px`
- 高 `40 CSS px`

布局完成之后，绘制到 `DPR = 3` 的屏幕上时，大致会变成：

- 宽 `300` 个物理像素
- 高 `120` 个物理像素

所以页面“看起来还是 100px 宽”，但边缘会更细腻，因为浏览器可以用更多物理像素去表达这个 100px 的视觉宽度。

### 3.2 这也是为什么高分屏不等于页面更大

高分屏提高的是同样视觉尺寸下的绘制精度，不是让页面元素自动放大。

只要 viewport 和 CSS 布局宽度不变，`width: 100px` 的元素在视觉尺寸上仍然接近同样大小。变化的是它在硬件层面被绘制得更精细。

## 4. CSS 里的 `1px` 为什么不等于硬件上的 1 个点

这是另一个最容易误解的地方。

```css
border: 1px solid #ddd;
```

这里的 `1px` 是 1 个 CSS 像素，不是 1 个物理像素。

如果设备 `DPR = 2`，浏览器会尝试把这条边框映射到更高密度的物理像素网格上。实际显示时，它可能占据多个物理像素，或者通过抗锯齿和子像素策略来接近这个厚度。

这就是为什么在高清屏上，经常会出现“1px 边框看起来偏粗”这个问题。

这类问题属于视觉实现细节，不改变前面的基本关系：

- CSS 中的 `px` 是逻辑单位
- 屏幕上的最终显示是逻辑单位映射到物理像素后的结果

## 5. 图片为什么要准备 `1x`、`2x`、`3x`

理解了上面的映射关系，图片清晰度问题就很好解释了。

假设页面上有一张头像，样式是：

```css
.avatar {
  width: 80px;
  height: 80px;
}
```

布局时浏览器只知道：这张图占 `80 x 80 CSS px`。

如果设备 `DPR = 1`，那么 80 x 80 的位图通常足够。
如果设备 `DPR = 2`，同样视觉尺寸下，屏幕实际可用于绘制的物理像素变成了大约 160 x 160。
如果仍然只给浏览器一张 80 x 80 的位图，它只能放大显示，结果通常会变糊。

这就是 `srcset` 的意义：

```html
<img
  src="/avatar@1x.png"
  srcset="/avatar@1x.png 1x, /avatar@2x.png 2x, /avatar@3x.png 3x"
  alt="avatar"
/>
```

这里不是在“适配某一款手机”，而是在告诉浏览器：

- 如果当前像素密度更高，可以选更高分辨率的资源

## 6. canvas 为什么总要单独处理 DPR

普通 DOM 元素的绘制映射由浏览器自动处理，但 `canvas` 不一样。`canvas` 有两个尺寸体系：

- CSS 尺寸：页面里占多大
- 绘图缓冲区尺寸：内部实际绘制分辨率

如果只设 CSS 尺寸，不按 DPR 放大缓冲区，高分屏下的 canvas 内容通常会发虚。

例如一个视觉上 300 x 150 的 canvas：

```html
<canvas id="chart" style="width: 300px; height: 150px;"></canvas>
```

更稳的做法通常是：

```js
const canvas = document.getElementById('chart');
const ctx = canvas.getContext('2d');
const dpr = window.devicePixelRatio || 1;

const cssWidth = 300;
const cssHeight = 150;

canvas.style.width = `${cssWidth}px`;
canvas.style.height = `${cssHeight}px`;
canvas.width = cssWidth * dpr;
canvas.height = cssHeight * dpr;

ctx.scale(dpr, dpr);
```

这段代码做了两件事：

1. 保持页面里还是 `300 x 150 CSS px`
2. 把内部绘制分辨率提升到更高的物理像素级别

这就是“布局尺寸不变，但绘制精度提升”的一个非常直接的例子。

## 7. 说响应式布局之前，要先搞清楚 viewport

如果没有 viewport，前面关于 CSS 像素的理解会直接乱掉。

移动端页面通常应包含：

```html
<meta name="viewport" content="width=device-width, initial-scale=1" />
```

这行配置的作用很实际：

- 告诉浏览器页面宽度应按设备逻辑宽度处理
- 告诉浏览器初始缩放比例是 1

没有它时，移动端浏览器可能按桌面页面宽度去缩放整页，导致：

- 页面整体被缩小
- 媒体查询和实际视觉效果不一致
- CSS 宽度判断失真

所以谈移动端适配，viewport 是前置条件，不是可选项。

## 8. 为什么响应式布局主要看逻辑宽度，而不是看设备型号

页面布局真正关心的是：

- 当前 viewport 有多宽
- 内容能否在这块空间里排开
- 组件在这个宽度下是否还保持可读和可操作

这几个问题都发生在 CSS 像素层，不发生在设备型号层。

举个很直接的例子：

如果两个设备最终提供给浏览器的逻辑宽度都接近 `390 CSS px`，那它们在大多数布局判断上就是同一类设备，即使它们的：

- 物理分辨率不同
- PPI 不同
- 品牌不同
- 型号不同

这就是为什么现代响应式布局不会围绕“iPhone 15、Pixel、某某安卓机型”去写条件分支，而是围绕：

- `min-width`
- `max-width`
- 内容最小宽度
- 容器可用空间

来组织布局。

## 9. 响应式布局真正响应的是什么

从实现角度看，响应式布局主要响应三件事。

### 9.1 可用空间

空间不够时，布局需要重排。

最典型的是：

- 三栏变两栏
- 两栏变一栏
- 导航横排变抽屉

这类变化通常使用媒体查询或容器查询。

### 9.2 内容密度

宽度变小时，不只是列数变化，内容密度也要变化：

- 行长变短
- 卡片信息减少
- 辅助信息折叠
- 操作入口合并

这部分不是纯布局问题，而是信息组织问题。

### 9.3 交互方式

有些变化不是因为屏幕物理尺寸，而是因为当前设备更适合触控、滑动或分段展开。

这部分可以辅助参考平台能力，但主逻辑仍然应建立在可用空间和组件行为上，而不是设备型号表。

## 10. 常见响应式方案，分别解决什么问题

### 10.1 媒体查询：页面级结构切换

媒体查询最适合做“大结构变化”。

例如：

```css
.layout {
  display: grid;
  grid-template-columns: 1fr;
}

@media (min-width: 768px) {
  .layout {
    grid-template-columns: 240px 1fr;
  }
}

@media (min-width: 1200px) {
  .layout {
    grid-template-columns: 240px 1fr 320px;
  }
}
```

这段代码表达的是：

- 小宽度下单栏
- 中等宽度下左侧导航 + 主内容
- 大宽度下再增加右侧信息栏

这里所有判断都基于 CSS 宽度，不关心硬件到底是多少物理像素。

### 10.2 Flex 和 Grid：减少硬断点

如果媒体查询负责“什么时候变结构”，那 `flex` 和 `grid` 更像在处理“结构内怎么分配空间”。

例如：

```css
.cards {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(240px, 1fr));
  gap: 16px;
}
```

这里的逻辑是：

- 每张卡片最小 240px
- 如果空间够，多排几列
- 如果空间不够，就自动减少列数

这类写法的好处是，它直接围绕内容最小宽度写规则，比维护一长串设备断点更稳定。

### 10.3 相对单位：让尺寸在范围内变化

响应式布局里常见的相对单位和函数包括：

- `%`
- `fr`
- `rem`
- `vw`
- `vh`
- `clamp()`

例如：

```css
.title {
  font-size: clamp(1.5rem, 1.1rem + 1.5vw, 2.5rem);
}
```

这段代码的含义是：

- 字号有最小值
- 中间会随着 viewport 宽度增长
- 到达上限后停止继续变大

这比为每个宽度单独写一组字号规则更平滑。

### 10.4 容器查询：组件级适配

媒体查询只看 viewport，有时并不够。

例如同一个卡片组件：

- 在首页瀑布流里只有 320px 宽
- 在详情页侧栏里只有 280px 宽
- 在桌面主内容区里可能有 560px 宽

这时候更合理的判断对象不是整个页面，而是组件自己的容器。

```css
@container (min-width: 480px) {
  .product-card {
    grid-template-columns: 120px 1fr;
  }
}
```

容器查询解决的是“组件放到不同位置时，怎么按自己的可用空间适配”。

## 11. rem 适配为什么曾经流行，现在又没那么主流了

移动端早期常见一种方案：把 `html` 根字号和 viewport 宽度绑定，然后页面中大量尺寸都写成 `rem`。

例如：

```js
document.documentElement.style.fontSize = `${window.innerWidth / 10}px`;
```

然后样式写成：

```css
.box {
  width: 3.2rem;
  padding: 0.24rem;
}
```

它流行的原因很简单：

- 可以把设计稿尺寸按比例换算
- 一套移动稿很容易整体缩放

但它的问题也很明显：

- 它把很多本该独立决定的尺寸绑在了同一套缩放规则上
- 对文本可读性不够友好
- 到了平板和桌面场景，扩展成本会上升

所以现在更常见的做法不是“整页跟着屏宽线性缩放”，而是：

- 页面结构用媒体查询
- 组件宽度用 flex/grid
- 字号和间距用 `rem`、`clamp()` 等工具分别控制

这套方式更细，也更稳。

## 12. 工程里哪些地方需要特别考虑 DPR

不是所有前端问题都要谈 DPR。大多数布局问题只看 CSS 像素就够了。

真正需要特别考虑 DPR 的场景通常有这几类：

### 12.1 位图资源

高密度屏幕下如果没有更高分辨率资源，图片容易发糊。

### 12.2 Canvas

如果不放大内部绘制缓冲区，canvas 内容通常会模糊。

### 12.3 精细线条

例如 hairline border、图表坐标线、微细分隔线。

### 12.4 缩放和截图相关逻辑

例如：

- 浏览器缩放后 `devicePixelRatio` 变化
- 画布导出尺寸
- 页面截图工具

这些场景如果忽略 DPR，结果经常会偏差很大。

## 13. 落到项目里，优先定这几条规则

如果项目里经常出现“为什么这个设备上看起来不一样”“为什么这张图糊了”“为什么这里要用这个断点”这类讨论，通常说明基础规则还没有统一。

更稳的做法是先明确下面几点：

1. 布局和断点讨论统一使用 CSS 像素，不用物理分辨率做页面规则。
2. 响应式方案优先围绕内容和可用空间，不围绕设备型号。
3. 页面级变化用媒体查询，组件级变化优先考虑容器查询。
4. 图片和 canvas 单独处理 DPR，不能用普通 DOM 的直觉去套。
5. viewport 设置、高清图策略和常用尺寸单位在项目里统一约定。

这几条一旦清楚，后面再讨论适配和清晰度问题，团队至少会站在同一个坐标系里。
