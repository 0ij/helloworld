如果让我只挑一个关键词来概括 React 16 之后的内部变化，我会选 **Fiber**。

因为从 React 16 开始，React 的重点就不再只是“怎么把 JSX 变成 DOM”，而是：

- 更新任务怎么拆分
- 哪些更新应该先做
- 哪些更新可以晚一点做
- 渲染过程中能不能打断、恢复、重试

也就是说，React 从“渲染库”逐渐变成了一个更像运行时调度器的东西。

这篇文章里，我想把自己对 React 原理的理解整理成一条比较清晰的线：

1. 为什么要有 Fiber
2. React 16 的 Fiber 到底解决了什么
3. React 18 在 Fiber 之上又改了什么
4. 为什么很多人觉得 React 18 才真正把 Fiber 的潜力释放出来

## 1. 先说结论：Fiber 不是一个功能点，而是一种新的工作单元模型

很多人第一次听到 Fiber，会把它理解成“React 的新 diff 算法”。

我觉得这个理解不够准确。

Fiber 更像是 React 内部对“渲染工作”的一种重新建模：

- 每个组件对应一个 Fiber 节点
- 每个 Fiber 节点保存当前组件的类型、状态、更新、子树关系和副作用信息
- 整个渲染过程不再必须一次性递归到底，而是可以按 Fiber 节点为单位拆分、暂停和恢复

换句话说，Fiber 的核心价值不是“更快”，而是“**更可调度**”。

## 2. 为什么 React 早期模型不够用

在 React 16 之前，Stack Reconciler 的主要问题是：

- 渲染过程基本是同步递归调用
- 一旦开始更新，就很难中途停下来
- 大树更新时，主线程会被长时间占住

这在应用变复杂以后会带来明显问题：

- 输入卡顿
- 动画掉帧
- 高优先级交互被低优先级渲染拖住

React 团队真正想解决的问题其实是：

> 页面渲染能不能像操作系统调度任务一样，被切片、打断、恢复，并按优先级安排？

Fiber 就是围绕这个目标设计出来的。

## 3. React 16：Fiber 正式落地，但整体仍偏“同步世界”

React 16 是 Fiber 第一次真正进入生产环境的大版本。

从外部 API 看，它带来了：

- 错误边界
- Fragments
- Portals
- 后来的 16.8 Hooks

但从内部机制看，更重要的是 React 已经不再用旧的 Stack Reconciler，而改成了 Fiber 树。

### 3.1 React 16 的核心变化

我会把 React 16 的 Fiber 重点概括成四件事：

#### 3.1.1 渲染单元从“调用栈”变成“链表节点”

Fiber 节点本质上是一个可中断、可恢复的工作单元。

它至少让 React 获得了两种以前很难做的能力：

- 可以在节点级别保存中间状态
- 可以把“下一步做什么”挂在节点之间，而不是完全依赖 JS 调用栈

这让 React 有机会在未来实现时间切片和优先级调度。

#### 3.1.2 双缓冲树（current / workInProgress）

Fiber 常见的一个理解入口，就是 React 同时维护：

- 当前屏幕上已经提交的树
- 正在内存里计算的新树

也就是常说的：

- `current`
- `workInProgress`

这样 React 就可以先在内存里把一整轮更新算出来，最后再统一提交到 DOM。

这也是为什么 React 会把工作分成两个阶段：

- Render 阶段：计算新树，可中断
- Commit 阶段：真正改 DOM，不可中断

#### 3.1.3 副作用收集

React 16 会在 Fiber 节点上收集副作用，然后在 commit 阶段集中处理。

这里的思想非常重要：

- render 阶段尽量只做计算
- commit 阶段再做真实副作用

这使得 React 的更新流程更可控，因为“算什么”和“改什么”被分离了。

#### 3.1.4 调度开始出现，但仍不彻底

虽然 Fiber 的目标包含可打断渲染，但 React 16 时代的实际体验仍然更接近“以同步渲染为主，调度能力刚起步”。

因为当时还有几个限制：

- 很多更新路径仍然偏同步
- root 模式还是 legacy root
- 优先级模型还不够细
- 大量用户代码默认按“立即完成渲染”心智在写

所以我会说：**React 16 把 Fiber 架子搭起来了，但还没有把并发能力全面释放出来。**

## 4. React 16 的优先级模型：Expiration Time

理解 React 16 和 React 18 差异，一个绕不过去的点就是优先级模型。

React 16 更典型的做法是：

- 给更新分配一个“过期时间”
- 根据时间先后和任务紧急程度决定何时处理

这个模型能工作，但问题也很明显：

- 表达能力不够细
- 很难自然表示“多批次更新共享部分优先级”
- 一些更新组合在一起时不够直观

简单说，它更像是：

- “这件事最晚什么时候必须做”

而不是：

- “这件事属于哪一类优先级通道”

这为 React 18 引入 lanes 埋下了伏笔。

## 5. React 18：Fiber 还是那个 Fiber，但调度体系已经不是一个时代了

很多人会说：“React 18 才是真正的并发 React。”

我觉得这句话大体成立。

不是因为 React 18 才有 Fiber，而是因为：

- React 18 把 Fiber 原本能承载的调度能力真正系统化了

最关键的变化点包括：

- `createRoot`
- Concurrent Rendering
- Lanes 优先级模型
- Automatic Batching
- Transitions
- Suspense 在客户端和服务端的进一步落地

## 6. React 16 和 React 18 最关键的 Fiber 对比

### 6.1 Root 模型：`render` vs `createRoot`

这是一个非常重要的分水岭。

React 16 时代，即便内部已经是 Fiber，应用大多数还是跑在 legacy root 上。

React 18 则通过：

```js
createRoot(container).render(<App />)
```

把一部分并发能力正式打开。

这意味着 React 18 不只是“换个 API”，而是：

- 通过新的 root 类型启用新的调度策略

从工程角度看，`createRoot` 是 React 18 并发能力的入口开关。

### 6.2 优先级模型：Expiration Time vs Lanes

这是我认为 Fiber 机制上最本质的一次升级。

#### React 16：Expiration Time

特点是：

- 用时间语义描述优先级
- 适合基本的任务先后安排
- 但对复杂更新组合不够自然

#### React 18：Lanes

React 18 改成了 lane 模型后，更新优先级更像“多条车道”：

- 不同更新进入不同 lane
- 多个 lane 可以并存
- React 可以合并、拆分或跳过某些 lane

这个模型的好处是：

- 更容易表示不同来源的更新
- 更适合并发渲染和可中断恢复
- 更方便做 transitions、deferred updates 这类能力

如果说 React 16 的调度更像“单轴时间线”，  
那 React 18 的 lanes 更像“多路优先级位图”。

这也是为什么 React 18 在复杂交互里更从容。

### 6.3 中断与恢复：从“可以做到”到“作为常规能力存在”

React 16 的 Fiber 已经为“可中断渲染”做了结构准备。

但 React 18 里，这件事才真正成为日常能力：

- 低优先级更新可以被更高优先级更新打断
- 中断后可以从未完成的 workInProgress 继续
- 不必每次都把整棵树从头算到底

这里要注意一个关键点：

React 从来没有允许 commit 阶段被打断。  
真正可中断的是 render 阶段。

所以 React 的并发，不是“DOM 一半改了一半没改”，而是：

- 计算过程可打断
- 提交过程仍然保持一致性

这是 React 能兼顾“体验”和“正确性”的关键。

### 6.4 批处理：React 16 更保守，React 18 更彻底

React 16 的批处理主要局限在 React 事件系统内部。

比如：

- 在 React 合成事件里，多次 `setState` 往往会被合并
- 但到了 `setTimeout`、`Promise`、原生事件里，批处理表现就没那么统一

React 18 则把 automatic batching 扩大了范围。

这意味着你在更多异步上下文里写：

```js
setA(...)
setB(...)
```

React 都会更倾向于合并处理，而不是各自触发一次独立渲染。

这件事表面上像性能优化，实际上反映的是：

- React 18 对更新调度的统一掌控变强了

### 6.5 过渡更新：React 18 正式把“用户感知优先级”引入 API

React 16 时代，优先级主要是 React 内部在决定。

React 18 则通过 `startTransition` 这样的 API，让开发者能更明确地表达：

- 这个更新是紧急的
- 这个更新可以晚一点

这很重要，因为它把“调度意图”从 React 内部暴露到应用层了。

例如：

- 输入框文本更新应当立刻响应
- 搜索结果列表更新可以稍后完成

这类场景在 React 18 里终于有了比较正交的表达方式。

### 6.6 Suspense：从局部能力走向更完整的并发配套

React 16 的 Suspense 更多还是实验性和局部能力。

到了 React 18，它和下面这些能力开始真正形成配合：

- 并发渲染
- 选择性 hydration
- 流式服务端渲染
- `useDeferredValue`
- transitions

所以 React 18 的 Fiber 不只是“能暂停”，而是开始形成一整套围绕等待、降级、恢复和优先级切换的用户体验模型。

## 7. 一个更底层的区别：React 16 在“引入 Fiber”，React 18 在“用好 Fiber”

我自己理解 React 16 和 React 18 的最大差异，不是有没有 Fiber，而是 Fiber 在系统中的成熟度不同。

### React 16 更像：

- 先把底层工作单元模型换掉
- 给未来的调度能力打基础
- 逐步把渲染流程拆成 render / commit

### React 18 更像：

- 在这个模型上重新设计更新优先级体系
- 把并发能力变成正式生产能力
- 让开发者能显式参与更新优先级表达

所以我会说：

> React 16 是 Fiber 的架构落地，React 18 是 Fiber 的调度体系成型。

## 8. 为什么 React 18 以后，理解 Fiber 变得更重要

如果你只写简单页面，可能感知不到这些差异。

但一旦场景涉及：

- 搜索联想
- 大列表过滤
- Suspense 数据加载
- SSR + Hydration
- 复杂表单
- 高交互后台系统

你会发现 React 18 的很多表现都和 Fiber 调度直接相关。

比如常见问题：

- 为什么某些更新看起来“延后了”？
- 为什么同样是 `setState`，有的更新很快，有的像被让路了？
- 为什么 `startTransition` 能改善输入卡顿？
- 为什么 `createRoot` 之后应用行为和以前有细微差别？

这些问题如果不回到 Fiber，很难真正理解。

## 9. 如果我要用一句话概括 React 16 到 18 的变化

我的概括是：

> React 16 用 Fiber 重写了渲染底座，React 18 则在这个底座上把“优先级调度、可中断更新、过渡渲染和更彻底的批处理”真正做成了日常能力。

它们不是彼此割裂的两个世界，而是同一条技术路线上的两个阶段：

- React 16：把“可调度的渲染系统”做出来
- React 18：把“可调度”变成用户真实能感知到的体验提升

## 10. 我自己的理解落点

现在再回头看，我会把 React 理解成三层：

- 表层是组件和 Hooks
- 中层是 reconciliation、state update、effects
- 底层是 Fiber 这套工作单元和调度机制

而 React 16 到 React 18 的演进，本质上就是：

- 底层调度能力越来越强
- 中层更新语义越来越统一
- 表层 API 逐渐把这些能力暴露给开发者

这也是为什么我越来越觉得：  
理解 React，不能只停在“会写 Hooks”，还得知道更新为什么会以那样的顺序发生。
