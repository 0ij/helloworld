## 1. 问题范围

这篇文章讨论的不是“AI 能不能写一个虚拟列表”，而是另一个更实际的问题：

- 在一个前端 React 项目里，如何让 AI coding 工具稳定地产出可用代码
- 如何减少来回纠错的对话轮次
- 如何减少因为需求不清和约束缺失带来的 token 浪费
- 如何让工程师保留对实现质量和边界条件的控制权

例子选用虚拟列表，是因为它同时包含了几类典型问题：

- 有明确的性能目标
- 有比较清楚的接口边界
- 容易出现隐藏 bug
- 既适合 AI 生成初稿，也很容易因为约束缺失而反复返工

如果只给 AI 一句“帮我写一个 React 虚拟列表组件”，通常也能产出一版代码。但这种方式的问题也很明显：

- 需求默认是模糊的
- 约束默认是缺失的
- AI 会自己补全很多你没有确认的决策
- 后续每一轮纠偏都要重复解释上下文

这类工作方式就是典型的 `vibe coding`。它适合探索，不适合稳定交付。

## 2. 这里说的 harness 是什么

最近一段时间，OpenAI 和 Thoughtworks 都在系统讨论 `harness engineering` 这个概念。这里可以先给一个工程化定义：

> harness 不是单条 prompt，也不是一份规则文件。它是一组围绕 AI coding agent 设计的输入约束、上下文组织、验证机制和反馈回路。

如果把它拆开看，通常至少包含四部分：

1. 任务定义
2. 代码和文档上下文
3. 自动验证手段
4. 失败后的收敛机制

这个定义和纯粹的 `vibe coding` 有一个关键区别：

- `vibe coding` 把重点放在“让 AI 尽快开始写”
- `harness` 把重点放在“让 AI 在可控边界里写”

对于前端项目，这个区别非常重要。因为前端 UI 很容易出现一种情况：

- 代码能跑
- 页面能打开
- 交互也基本存在

但真正需要的细节并没有被满足，例如：

- 滚动窗口计算不稳定
- 列表底部出现空白
- resize 后位置错误
- `key` 使用不当导致状态错乱
- 可访问性缺失
- 边界条件没有覆盖

这些问题如果放在多轮对话里修，token 消耗会非常快。

## 3. 为什么虚拟列表适合拿来讲 AI coding 的控制问题

虚拟列表的目标通常很明确：

- 只渲染可视区域附近的列表项
- 保持滚动体验稳定
- 降低大列表下的 DOM 数量和渲染成本

但它的实现空间并不小。至少有这些决策点：

- 固定高度还是动态高度
- overscan 多少
- 用绝对定位还是 transform
- 如何处理 resize
- 滚动事件自己算，还是依赖浏览器观察能力
- 是否支持横向
- 是否支持自定义容器
- 是否暴露 imperative API

如果这些决策没有提前定下来，AI 会默认替你做决定。后果通常不是“写不出来”，而是“写出来以后再返工”。

所以虚拟列表非常适合用来说明一个原则：

> 减少对话轮次，不靠更会聊天，而靠更早把任务收敛成一个可执行的约束集合。

## 4. 在让 AI 动手前，先把任务收敛成一个最小规格

如果目标是减少轮次和 token 浪费，不要把第一条消息写成开放式需求。先把项目任务收敛成最小规格，再交给 AI。

以一个固定高度虚拟列表为例，规格至少应明确下面这些内容。

### 4.1 功能范围

```text
实现一个 React + TypeScript 的 VirtualList 组件。

本次只支持固定高度 item。
支持垂直滚动。
支持容器高度传入。
支持 overscan。
支持通过 renderItem 渲染内容。
```

### 4.2 非目标

```text
本次不支持动态高度。
不支持瀑布流。
不支持无限加载。
不支持键盘导航。
不引入第三方虚拟列表库。
```

### 4.3 接口定义

```tsx
type VirtualListProps<T> = {
  items: T[];
  itemHeight: number;
  height: number;
  overscan?: number;
  itemKey?: (item: T, index: number) => string | number;
  renderItem: (item: T, index: number) => React.ReactNode;
};
```

### 4.4 验收条件

```text
10000 条数据下滚动时不应渲染全部节点。
滚动到底部时不应出现明显空白区。
改变容器高度后可视区计算应正确。
首屏应只渲染可见区和 overscan 范围内的节点。
build 和 check 必须通过。
```

### 4.5 代码约束

```text
使用函数组件和 hooks。
保持组件职责单一。
计算逻辑和渲染逻辑分开。
避免过早抽象。
不要为了“性能优化”引入不必要的 useMemo/useCallback。
```

这一步的意义不是写文档本身，而是把后续高频重复解释的内容前置。

## 5. 把规格写进仓库，比把它留在聊天窗口里更划算

如果一个任务会超过一两轮对话，规格最好进入仓库，而不是只存在于聊天记录里。

例如，可以放一个文件：

```text
docs/virtual-list-spec.md
```

内容包括：

- 目标
- 非目标
- 组件接口
- 验收条件
- 性能约束
- 已知边界

这样做有三个直接收益：

1. 后续任务不需要反复复制需求。
2. AI 可以直接引用仓库内的规格，而不是依赖聊天上下文窗口。
3. 规格和代码可以一起演进，降低“聊天里说过但仓库里没有”的信息丢失。

这也是 harness 的第一层：把任务说明从临时对话提升成可版本化的工程输入。

## 6. 一个更省轮次的 AI 任务包应该长什么样

如果规格已经在仓库里，第一条真正让 AI 写代码的消息就不应该再是开放式描述，而应该是一个完整任务包。

下面是一种更适合前端项目的写法：

```text
基于 docs/virtual-list-spec.md 实现第一版 VirtualList。

要求：
1. 只实现固定高度虚拟列表。
2. 代码放在 src/components/VirtualList.tsx。
3. 如有必要，可新增一个最小 demo 页面用于手动验证。
4. 不引入第三方虚拟列表依赖。
5. 提交前执行 npm run build 和 npm run check。

输出要求：
1. 先说明计划修改哪些文件。
2. 再实现代码。
3. 最后说明如何验证滚动窗口计算。
```

这类 prompt 的特点是：

- 输入边界清楚
- 输出格式清楚
- 文件范围清楚
- 验证要求清楚

这样 AI 不需要花很多 token 去猜你的工作方式。

## 7. 减少轮次，不是让一条 prompt 更长，而是让缺失信息更少

很多人为了减少对话轮次，会尝试把第一条 prompt 写得特别长。但如果信息组织不清楚，长 prompt 仍然会浪费 token。

更有效的做法是把输入拆成四类信息：

### 7.1 任务目标

告诉 AI 这次交付什么，不交付什么。

### 7.2 项目约束

告诉 AI 你的技术栈、文件位置、编码风格、依赖边界。

### 7.3 验证方式

告诉 AI 什么命令可以证明实现是否成立。

### 7.4 输出格式

告诉 AI 需要先计划、再修改、再汇报，而不是直接吐一大段代码。

如果这四类信息齐全，prompt 不必很长，对话轮次也会明显减少。

## 8. 面向虚拟列表任务，harness 应该包含哪些内容

把这个例子继续往前推，一个更完整的虚拟列表 harness 可以设计成下面这几层。

### 8.1 Guides：约束和说明

Guides 用来缩小实现空间，避免 AI 自行扩展需求。

建议至少包含：

- `docs/virtual-list-spec.md`
- 项目级写作和编码规范
- 组件目录约定
- 性能目标和非目标列表

### 8.2 Sensors：自动验证点

Sensors 用来回答“这次修改到底有没有满足要求”。

对于虚拟列表，建议至少有：

- `npm run build`
- `npm run check`
- 一个 demo 页面
- 一个渲染节点数量检查
- 一个滚动到底部的手动验证路径

如果项目允许，还可以加：

- 简单的组件测试
- 滚动窗口计算单测
- screenshot 或录屏校验

### 8.3 Structural constraints：结构约束

结构约束的作用是限制 AI 生成“能跑但难维护”的代码。

例如：

- 虚拟区间计算抽成纯函数
- 组件渲染层不直接混入复杂边界判断
- demo 页面和组件逻辑分开
- 不允许把性能测试代码混入正式组件

### 8.4 Feedback loop：失败后怎么收敛

harness 不是“有了验证就结束”，还要定义失败后的处理方式。

例如：

- 如果 `build` 失败，先修类型和导入问题
- 如果滚动到底部有空白，优先检查区间计算和 total height
- 如果渲染节点过多，检查可视窗口和 overscan 是否失控
- 如果组件逻辑变复杂，把区间计算移入独立函数并补测试

这部分内容可以写进 spec，也可以沉淀到技能文件或开发说明里。

## 9. 一个适合 AI 的实现拆分

虚拟列表如果一次性让 AI 全做完，仍然可能产出一版过度复杂的实现。更稳的做法是按可验证节点拆分。

推荐拆成下面几个任务。

### 9.1 第一步：搭接口和最小渲染骨架

目标：

- 定义 `VirtualListProps`
- 建立滚动容器
- 建立总高度占位
- 先用最简单的可视区计算跑通

验证：

- demo 页面能渲染
- 大列表不再一次性挂出全部节点

### 9.2 第二步：把区间计算抽成纯函数

目标：

- 根据 `scrollTop`、`itemHeight`、`height`、`overscan` 计算 start / end

验证：

- 补单测或最小断言
- 校验顶部、底部、边界 overscan

### 9.3 第三步：补 resize 和边界处理

目标：

- 容器高度变化后重新计算
- 处理空数组、overscan 异常值、itemHeight 非法值

验证：

- 修改 demo 参数后行为稳定

### 9.4 第四步：再做代码整理

目标：

- 去掉无意义抽象
- 统一命名
- 检查 key 生成和渲染稳定性

验证：

- build/check 通过
- 代码结构和 spec 对齐

这种拆分方式的好处是每一轮都能结束在一个可验证状态，而不是在长对话里不断漂移。

## 10. 哪些 prompt 会明显浪费 token

下面几类写法很容易让 AI coding 进入高消耗、低控制的状态。

### 10.1 目标太大，但边界没写

```text
帮我做一个功能完整、性能很好的虚拟列表组件。
```

问题在于：

- “功能完整”没有定义
- “性能很好”没有指标
- AI 会自行决定支持范围

### 10.2 一轮对话里同时解决产品、设计和实现

```text
顺便把列表样式也优化一下，最好再支持无限加载和动态高度。
```

这会把原本可控的组件任务重新变成开放式项目讨论。

### 10.3 在聊天里补约束，不把约束写回仓库

如果每次都在聊天里说：

- 这次不要抽 hook
- 这次不要上第三方库
- 这次要兼容空列表

那下一轮大概率还要重复。

更好的做法是把这些约束写回 spec 或项目规范。

### 10.4 把 review 变成继续聊天

不推荐这样：

```text
感觉还是不太对，你再改改。
```

更好的写法是：

```text
当前实现与 spec 有三处不一致：
1. 超出本次范围，加入了动态高度支持。
2. start/end 区间计算未单独抽出，难以验证。
3. demo 和正式组件逻辑耦合。

请按这三点收敛，不新增能力。
```

这类反馈的 token 利用率会高很多。

## 11. 工程师如何保持对 AI 产出的掌控度

掌控度不来自“少用 AI”，而来自“知道哪些点必须由人做判断”。

对于虚拟列表，这些点通常不应该完全交给 AI 自由发挥：

### 11.1 支持范围

固定高度还是动态高度，决定了实现复杂度和验证成本。这是需求边界，不是编码细节。

### 11.2 组件接口

props 设计一旦扩散，后面会直接影响调用方和可维护性。

### 11.3 性能目标

应该追求的是“限制 DOM 数量、稳定滚动窗口、避免无意义重算”，而不是泛化地要求“更高性能”。

### 11.4 验证方式

AI 可以执行检查，但“什么算通过”必须先由人定义。

### 11.5 最终 review

人至少要检查这些点：

- 区间计算是否正确
- `key` 是否稳定
- 空列表和底部边界是否处理
- 是否偷偷实现了 spec 之外的能力
- 是否为了“聪明”引入了难维护抽象

这里的核心不是逐行手写代码，而是逐项检查约束是否被满足。

## 12. 一个更推荐的工作流

如果把这篇文章收敛成一个更稳定的工作流，可以是下面这个顺序。

1. 先把需求写成最小规格，明确目标和非目标。
2. 把规格写进仓库，而不是只留在聊天窗口。
3. 为任务准备最小验证手段，例如 demo、build、check、单测。
4. 用完整任务包让 AI 实现第一版，而不是开放式聊天。
5. 每轮反馈都引用 spec 中的具体不一致项，不追加新的模糊要求。
6. 把高频约束沉淀回仓库，避免下一轮重复消耗 token。

这种工作流和纯粹的 vibe coding 最大的区别，不在于模型能力，而在于工程输入的质量。
