前端里有一类知识，经常被大家认为“很基础”，于是反而容易被一带而过。

字体和图标就是这样。

很多人会用：

- `font-family`
- `font-size`
- `@font-face`
- iconfont
- SVG 图标

但如果继续往下问几层，常常就会开始模糊：

- 字体文件到底是怎么被浏览器加载的？
- 为什么同一段文字在不同设备上看起来不一样？
- 为什么有时候你明明设置了某个字体，但最终显示的不是它？
- 图标和字体为什么经常会一起讨论？
- 如果项目里要统一图标，`Icon` 组件到底该怎么设计？

这篇文章我想把这几件事顺着讲清楚。

如果只先给一个结论，我会这样概括：

> 字体和图标看起来是两个话题，但它们在前端里的很多工程处理方式是相通的，本质上都和“资源引入、默认回退、尺寸控制、颜色继承、组件封装”有关。

## 1. 浏览器里的字体不是“天然存在”，而是一个选择和回退过程

很多人刚接触前端时，会把字体理解成一个简单属性：

```css
body {
  font-family: Arial;
}
```

但浏览器真正做的事情，其实比这复杂一点。

当浏览器要渲染一段文本时，它通常会经历这样一个过程：

1. 先看你声明了什么字体族。
2. 再看当前设备或系统里有没有这个字体。
3. 如果没有，就继续往后找回退字体。
4. 如果都没有，就落到通用字体族，比如 `sans-serif`、`serif`、`monospace`。
5. 如果当前字体缺某些字形，比如中文、日文、emoji，也可能再单独回退到别的字体补字形。

也就是说，`font-family` 很多时候不是“指定一个字体”，而是“给浏览器一串候选方案”。

## 2. 字体文件怎么引入

前端里常见的字体来源，大致有三类：

- 依赖用户设备里已经安装的系统字体
- 项目自己托管 web font 文件
- 使用第三方字体服务

### 2.1 直接使用系统字体

这是最轻量的方式。

比如你写：

```css
body {
  font-family: -apple-system, BlinkMacSystemFont, "Segoe UI", "PingFang SC", "Microsoft YaHei", sans-serif;
}
```

这段配置的意思不是“必须用第一种字体”，而是：

- 在 macOS / iOS 上优先走系统 UI 字体
- 在 Windows 上尽量回退到 `Segoe UI` 或常见中文字体
- 最后再回退到通用无衬线字体

这种方式的好处很直接：

- 不需要额外下载字体资源
- 加载快
- 更接近各平台原生界面风格

但代价也很明显：

- 跨设备的视觉一致性会弱一些
- 不同系统的字重、字宽、字形细节可能差异明显

### 2.2 用 `@font-face` 引入字体文件

如果你希望品牌字体、标题字体或者某种特殊字形在不同设备上尽量统一，就要自己引入字体文件。

最常见的方式是：

```css
@font-face {
  font-family: "Inter";
  src:
    url("/fonts/Inter-Regular.woff2") format("woff2"),
    url("/fonts/Inter-Regular.woff") format("woff");
  font-weight: 400;
  font-style: normal;
  font-display: swap;
}
```

然后在页面里使用：

```css
body {
  font-family: "Inter", "PingFang SC", "Microsoft YaHei", sans-serif;
}
```

这里有几个关键点值得特别注意。

#### `font-family`

这是你给这份字体起的名字，不一定非要等于字体文件本名。

#### `src`

这里声明具体字体资源地址和格式。现代前端项目里通常优先放 `woff2`，必要时再补 `woff` 兼容。

#### `font-weight` 和 `font-style`

它们不是装饰信息，而是浏览器匹配字体的重要条件。

如果你有 Regular、Medium、Bold 三种字重，通常应该分别声明不同的 `@font-face` 记录，而不是只写一条。

#### `font-display`

这个属性很重要，它决定 web font 还没加载完成时文本怎么显示。

最常见的是：

- `swap`：先用回退字体显示，字体加载好后再替换
- `block`：先短暂隐藏文字，等字体加载
- `optional`：更偏性能优先，字体来不及就可能直接放弃切换

大多数内容型页面里，`swap` 往往是比较务实的选择。

### 2.3 第三方字体服务

比如从在线字体服务引入字体。

这种方式的优点是接入简单，但工程上要额外考虑：

- 网络稳定性
- 缓存策略
- 隐私与合规
- 首屏性能

如果项目本身是面向公开用户、且字体对品牌很关键，很多团队最后还是会选择自托管字体文件。

## 3. 为什么不同设备上字体看起来不一样

这是前端里很常见的一个现象。

你明明写的是同一份 CSS，但在不同设备上：

- 字显得更宽或更窄
- 字重看起来更粗或更细
- 行高感觉不一样
- 中英文混排的节奏不同

原因通常不是单一的，而是几件事叠加：

### 3.1 系统默认字体不同

不同系统天然自带不同字体族。

比如你没有明确指定时，浏览器会根据平台和语言环境选默认字体。

于是：

- macOS
- Windows
- Android
- iOS

它们对同一段中文或英文的默认呈现很可能并不一样。

### 3.2 字体回退链不同

即便你声明了一串 `font-family`，每台设备真正命中的字体也可能不同。

例如：

```css
font-family: "Inter", "PingFang SC", "Microsoft YaHei", sans-serif;
```

在不同设备上，可能出现：

- 英文命中 `Inter`
- 中文字形落到 `PingFang SC`
- 某些机器没有这套中文字体，于是回退到 `Microsoft YaHei`
- emoji 又再回退到系统 emoji 字体

所以最终看到的并不是一份“单一字体渲染结果”，而是一组字体共同完成的渲染结果。

### 3.3 字体本身的 metrics 不同

不同字体的这些指标不一样：

- ascent
- descent
- x-height
- 字面宽度
- 默认行盒占比

所以同样 `font-size: 16px`，不同字体看起来视觉大小可能并不一致。

这也是为什么只改 `font-family`，页面排版有时会跟着发生轻微位移。

### 3.4 浏览器和系统渲染策略不同

不同平台的字体抗锯齿、hinting、字重渲染也会有差异。

这类差异前端通常很难完全抹平，所以更现实的目标往往不是“每台设备像素级完全一致”，而是：

> 建立一套稳定的字体回退策略，让视觉差异保持在可接受范围内。

## 4. 前端里更实用的字体设置思路

如果不是做特别强品牌表达的页面，我会更推荐这样想字体策略：

### 4.1 正文字体优先考虑可读性和系统适配

正文不是海报，它首先要解决长时间阅读是否舒服。

所以正文很多时候更适合：

- 系统字体栈
- 或者只给英文用 web font，中文继续用系统常见字体

例如：

```css
body {
  font-family:
    "Inter",
    -apple-system,
    BlinkMacSystemFont,
    "Segoe UI",
    "PingFang SC",
    "Hiragino Sans GB",
    "Microsoft YaHei",
    sans-serif;
}
```

### 4.2 标题字体可以更强调品牌或风格

标题通常字量更少、权重更高，更适合使用品牌字体或更有识别度的字体。

这时候自定义字体文件会更有价值。

### 4.3 不要只配英文字体，不管中文回退

这是很常见的疏漏。

很多人引了一个英文 web font，就觉得字体系统配置完了。但对中文页面来说，真正影响体验的往往是：

- 中文最终回退到哪套字体
- 中英文混排时风格是不是太割裂

所以字体策略最好把多语言场景一起想进去。

## 5. 图标为什么总和字体一起讨论

因为它们在前端里有很多相似点。

先说结论：

> 图标虽然是图形资源，但在页面中的使用方式，常常和文字非常接近。

它们的相似之处主要体现在下面几个方面。

### 5.1 都要被“引入”和“注册”

字体要通过系统安装、`@font-face` 或第三方服务引入。

图标也一样，要先有资源来源：

- iconfont 字体文件
- SVG 文件
- SVG sprite
- 组件化图标库

它们都不是浏览器“凭空就有”的。

### 5.2 都有默认回退问题

字体没命中时会回退到后面的字体族。

图标也有自己的“回退”问题，只是表现方式不同：

- iconfont 没加载成功时，可能显示成方块或乱码
- SVG 图标路径不对时，可能完全不显示
- 图标组件名传错时，可能渲染空节点

也就是说，它们都需要“资源存在且能被正确解析”。

### 5.3 都有尺寸、颜色、对齐问题

文字会关心：

- `font-size`
- `line-height`
- `font-weight`
- `color`

图标其实也一样会关心：

- 宽高
- 视觉粗细
- 与文字基线如何对齐
- 是否继承文字颜色

尤其是现代前端里大量 SVG 图标，最推荐的做法之一就是让图标颜色走 `currentColor`，这样图标和文字的颜色系统就能自然统一。

例如：

```html
<svg viewBox="0 0 24 24" fill="none" stroke="currentColor">
```

这样父元素设了 `color`，图标通常就能自动跟着变色。

### 5.4 都适合做一层统一封装

项目里不会希望每个地方都自己写一遍：

- 具体字体栈
- 具体图标文件路径
- 尺寸换算
- 颜色设置

所以字体会被沉淀成全局 token、主题变量或 typography 系统。

图标也一样，最好有统一的 `Icon` 封装。

## 6. iconfont 和 SVG，到底该怎么选

聊图标封装之前，先要说一个现实问题：图标资源本身怎么表示。

前端常见的两条路是：

- iconfont
- SVG

### 6.1 iconfont 的优点和问题

iconfont 的历史很长，很多项目都用过。

它的优点是：

- 使用方式像字体
- 通过 `font-size`、`color` 控制很方便
- 一套字体文件里可以放很多图标

但它的问题也越来越明显：

- 多色图标表达能力弱
- 可访问性一般
- 某些字形映射不直观
- 调试时不如 SVG 直接
- 图标本质上被当成字符，不够语义化

### 6.2 SVG 更适合现代组件化前端

现在更多项目会优先选 SVG，原因很现实：

- 可读性更好
- 控制更细
- 支持多色、描边、填充
- 更适合做组件封装
- 更容易和 React、Vue、Astro 这类组件模型结合

所以如果不是历史包袱很重，我通常更建议新项目优先考虑 SVG 方案。

## 7. 如果要封装 Icon，先想清楚封装目标

很多人一说“封装 Icon”，第一反应是做一个组件：

```jsx
<Icon name="search" />
```

这当然没错，但更重要的是先想清楚，你到底想通过封装解决什么问题。

我觉得通常至少是在解决这几件事：

- 图标资源入口统一
- 用法统一
- 尺寸和颜色控制统一
- 可访问性处理统一
- 未来替换资源方案时，业务层尽量少改

如果这几个目标不明确，组件很容易只变成一个薄薄的转发层。

## 8. 一个更实用的 Icon 组件设计思路

如果项目用的是 SVG 组件方案，一个比较常见也比较稳的封装思路是：

### 8.1 先做图标映射表

例如：

```ts
import SearchIcon from './icons/search.svg';
import CloseIcon from './icons/close.svg';
import ArrowRightIcon from './icons/arrow-right.svg';

export const icons = {
  search: SearchIcon,
  close: CloseIcon,
  arrowRight: ArrowRightIcon,
};
```

这样做的好处是：

- 资源来源集中
- 业务层不需要关心真实文件路径
- 后面要替换图标实现时更可控

### 8.2 再定义统一的 props

一个基础版 `Icon` 组件，我通常会优先考虑这些参数：

- `name`
- `size`
- `color`
- `className`
- `title`
- `aria-hidden`

例如：

```tsx
type IconName = keyof typeof icons;

interface IconProps {
  name: IconName;
  size?: number | string;
  color?: string;
  className?: string;
  title?: string;
}
```

### 8.3 尺寸和颜色尽量走统一规则

比如：

```tsx
export function Icon({
  name,
  size = 16,
  color = 'currentColor',
  className,
  title,
}: IconProps) {
  const SvgIcon = icons[name];

  return (
    <SvgIcon
      width={size}
      height={size}
      color={color}
      className={className}
      aria-hidden={title ? undefined : true}
      role={title ? 'img' : 'presentation'}
    />
  );
}
```

这里面我比较看重的点有三个。

第一，`size` 默认值统一。

这样各处图标不会因为“大家随手写不同尺寸”而失去节奏感。

第二，`color` 默认走 `currentColor`。

这样图标就能和文字颜色体系自然同步。

第三，把可访问性一起封装掉。

如果只是装饰图标，通常应该 `aria-hidden`；如果图标承担含义，比如状态图标或独立按钮图标，就应该给可读文本或 `title`。

## 9. Icon 封装时常见的几个坑

### 9.1 只做了名字转发，没有做设计约束

如果 `Icon` 组件只是：

```jsx
<Icon name="xxx" />
```

但尺寸、颜色、对齐、无障碍都还是各写各的，那它的价值其实很有限。

真正有价值的封装，不只是“统一入口”，还要统一约束。

### 9.2 图标和文字不对齐

这是特别常见的问题。

比如：

- 图标视觉中心不在中间
- 与文字基线不齐
- 行高变化时看起来上下漂

这类问题通常要配合处理：

- `display`
- `vertical-align`
- `line-height`
- 容器的 `align-items`

如果图标主要出现在按钮、链接、列表项前缀里，最好把这些组合样式一并沉淀下来，而不是只封装图标本身。

### 9.3 图标颜色没有跟随文本系统

如果每次都手动传具体色值，后面主题切换、暗色模式、状态色统一时会很痛苦。

所以默认走 `currentColor` 往往是非常划算的决定。

### 9.4 可访问性被忽略

图标常见的两种角色是：

- 纯装饰
- 有语义

如果是纯装饰，就不应该让读屏器反复读它。
如果图标本身承载语义，比如“成功”“警告”“关闭”，就应该给出明确的无障碍文本。

## 10. 图标和字体设置，为什么适合一起纳入设计系统

从工程角度看，这两者都不只是“资源文件”，而是界面语言的一部分。

它们都和下面这些事情有关：

- 品牌一致性
- 信息层级
- 视觉节奏
- 可读性
- 组件复用

所以更成熟的做法通常不是“某一页手动配一下字体、某个组件随便塞一个图标”，而是把它们一起纳入设计系统的基础层。

比如：

- 定义正文、标题、数字、代码等字体 token
- 定义图标尺寸 token，比如 `xs / sm / md / lg`
- 统一颜色继承规则
- 统一无障碍规则
- 统一资源组织方式

这样前端代码里真正消费的就不再是散乱资源，而是一套稳定接口。

## 11. 如果让我把这篇文章压缩成几条最重要的结论

我会留下这些：

1. `font-family` 很多时候不是指定一个字体，而是给浏览器一条回退链。
2. 不同设备上字体不一样，往往是系统默认字体、回退命中和字体 metrics 共同造成的。
3. 字体配置不能只看英文，要把中文和多语言回退一起考虑。
4. 图标和字体在工程上有很多相似点，本质上都要解决引入、回退、尺寸、颜色和统一封装。
5. 新项目里如果没有特殊历史包袱，图标通常更推荐优先考虑 SVG 方案。
6. `Icon` 组件真正的价值，不只是统一名字入口，而是统一尺寸、颜色、对齐和可访问性规则。

最后再收一句我自己的理解：

字体和图标之所以值得单独讲，不是因为它们复杂，而是因为它们足够基础。

越基础的东西，越会在整个项目里反复出现。也正因为反复出现，它们越值得在一开始就想清楚。
